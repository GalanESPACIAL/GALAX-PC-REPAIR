# GALAX PC REPAIR — migración a Supabase (PostgreSQL)

Archivos de esta carpeta (NO modificar ningún otro archivo del proyecto):

| Archivo | Contenido |
|---|---|
| `001_schema_postgres.sql` | DDL completo: 31 tablas (30 heredadas + `profiles`), PK/FK/índices, triggers `updated_at`, función de mapeo `auth.uid()` → `usuarios.id`, RLS y grants. |
| `002_seed_postgres.sql` | Todos los datos reales: 12 productos, 23 categorías, 6 servicios, 6 roles, 18 permisos, 43 `rol_permiso`, 18 configuraciones, 5 usuarios, 3 clientes, 4 `audit_log`, 5 migraciones. Todo `INSERT ... ON CONFLICT DO NOTHING`. |

## Cómo ejecutar en Supabase

1. En el proyecto de Supabase, abrir **SQL Editor** → **New query**.
2. Pegar y ejecutar `001_schema_postgres.sql` completo. Es idempotente (usa `IF NOT EXISTS`, `CREATE OR REPLACE`, `DROP POLICY IF EXISTS`).
3. Nueva query → pegar y ejecutar `002_seed_postgres.sql`. También idempotente: se puede repetir sin borrar ni duplicar datos.
4. Verificación rápida (las dos últimas sentencias del seed están comentadas):
   `productos=12, categorias=23, servicios=6, roles=6, permisos=18, rol_permiso=43, configuracion=18, usuarios=5, clientes=3`.
5. Opcional desde psql: `\pset pager off` y las mismas consultas de conteo.

No ejecutar los archivos MySQL (`database.sql`, `database/backups/*.sql`, `database/migrations/*.sql`) contra PostgreSQL: usan `DELIMITER`, `AUTO_INCREMENT`, `TINYINT(1)`, `ON DUPLICATE KEY UPDATE`, etc.

> Los archivos asumen el schema `public` de Supabase y que existe el schema `auth` (para `auth.users` y `auth.uid()`). No funcionan en un PostgreSQL sin Supabase Auth tal cual.

## Traducciones aplicadas

| MySQL | PostgreSQL |
|---|---|
| `AUTO_INCREMENT` | `GENERATED BY DEFAULT AS IDENTITY` (los seeds insertan ids explícitos; el seed ajusta todas las secuencias con `setval`). |
| `TINYINT(1)` | **`integer NOT NULL`**, nunca `boolean` (el PHP compara `= 1` / `= 0`). Defaults conservados: `publicado`, `servicios.activo`, `proveedores.activo` = 1; `destacado`, `es_nuevo`, `leida`, `es_interno`, `aprobacion_cliente` = 0. |
| `ENUM(...)` | `text` + `CHECK (...)` (incluye los 13 estados de `reparaciones`). |
| `DATETIME` / `TIMESTAMP` | `timestamptz` (las fechas del backup se cargan con sufijo `+00`). |
| `ON UPDATE CURRENT_TIMESTAMP` | trigger `BEFORE UPDATE` vía `public.gx_set_updated_at()`. |
| `ON DUPLICATE KEY UPDATE` / `INSERT IGNORE` | `ON CONFLICT (...) DO NOTHING`. Objetivos usados: `configuracion(clave)`, `rol_permiso(rol_id, permiso_id)`, ids PK en el resto. Plantilla para `carrito_items(carrito_id, producto_id)` incluida como comentario en el seed. |
| `utf8mb4` | UTF8 nativo. Se reparó el mojibake del volcado (`Gesti├│n` → `Gestión`, etc.) y se aplicaron las correcciones de la migración 004. |
| Procedimientos `DELIMITER` | No se migran: `gx_add_column`/`gx_add_index` sólo servían para aplicar migraciones sobre una BD ya existente; aquí el DDL es definitivo. |

## RLS (Row Level Security)

- RLS activado en las 31 tablas. **No** se usa `FORCE ROW LEVEL SECURITY`: el rol `service_role` (y cualquier conexión con `BYPASSRLS` usada por el backend PHP) sigue accediendo sin restricciones.
- Lectura pública: `productos` (`estado='activo' AND publicado=1`), `categorias` (`estado='activo'`), `servicios` (`activo=1`).
- `profiles`: cada usuario de Auth ve/inserta/actualiza **sólo su fila** (`auth.uid() = id`).
- Propiedad: `usuarios`, `clientes`, `carritos`, `carrito_items`, `carrito_historial`, `pedidos`, `pedido_detalles`, `garantias`, `reparaciones`, `reparacion_historial`, `reparacion_repuestos`, `tickets`, `respuestas_tickets`, `notificaciones`, `ai_conversaciones`, `ai_mensajes` usan `public.current_local_user_id()` (función `SECURITY DEFINER` que mapea `auth.uid()` → `usuarios.id` vía `usuarios.supabase_uid`).
- Notas internas de tickets (`es_interno=1`) no son visibles para clientes vía clave anon/authenticated; el panel PHP las lee con service role.
- Sin políticas (acceso sólo service_role/backend): `ventas`, `detalle_ventas`, `audit_log`, `migraciones`, `proveedores`, `compras_proveedor`, `inventario_movimientos`.
- `roles`, `permisos`, `rol_permiso` y `configuracion` son de lectura pública para `authenticated`.

## Pasos manuales posteriores a la importación

1. **Auth**: crear los usuarios de Supabase Auth (email + contraseña) desde Authentication → Users o con la Admin API. Activar/desactivar **email confirmation** según la política del proyecto (Authentication → Providers → Email → *Confirm email*). No hay contraseñas en texto plano en estos SQL.
2. **Vincular identidades**: para cada usuario Auth, copiar su `uuid` y ejecutar:
   ```sql
   UPDATE public.usuarios SET supabase_uid = '<uuid-auth>'
    WHERE email = 'admin@ventas.com';   -- o el email correspondiente
   ```
   Sin este paso, las políticas de propiedad devuelven false para ese usuario (el backend con service role sigue funcionando).
3. **Perfiles**: crear la fila de `profiles` del usuario (o hacerlo desde la app). Ejemplo:
   ```sql
   INSERT INTO public.profiles (id, nombre_completo)
   SELECT id, 'Administrador Sistema' FROM auth.users WHERE email = 'admin@ventas.com'
   ON CONFLICT (id) DO NOTHING;
   ```
4. **Configuración comercial**: revisar `configuracion.site_url` (por defecto `http://localhost/galax_pc_repair`), `promo_fin` (demo, vence 2026-11-22), `ai_api_url` y `whatsapp_numero`.
5. **Backend PHP**: `config/database.php` sigue construyendo un DSN `mysql:` y usa pdo_mysql. Para operar contra Supabase hay que migrar el código de conexión a `pdo_pgsql` (o `pgsql` vía PDO) y adaptar las sentencias MySQL-específicas del lado PHP. **Este cambio de código NO está incluido en estos archivos SQL**, por orden expresa de no modificar archivos existentes.
6. **Imágenes**: las rutas sembradas son las exactas del backup (`assets/img/productos/*.svg`). El roadmap (D15) documenta que en la BD final los productos 1 y 2 pasaron a `LAP-001.png` / `LAP-002.png`; hay un `UPDATE` opcional comentado en el seed si se quiere reproducir ese estado. No se inventaron rutas ni imágenes. Si los archivos se sirven desde Supabase Storage, hay que actualizar `product_image_url()` en PHP (fuera del alcance de estos SQL).
7. **Datos de QA**: no se siembran pedidos, reparaciones, tickets, carritos ni conversaciones IA: el roadmap confirma que se eliminaron antes del estado final. Sólo se conservan los 4 eventos reales de `audit_log`.

## Notas de integridad

- Se conservan los huecos de ids del origen (`categorias` 8, `configuracion` 11, `audit_log` 2) porque corresponden a filas borradas históricamente; no se renumeran datos reales.
- `clientes.usuario_id` sigue siendo `integer` con FK a `usuarios.id`; el enlace con Supabase Auth es invocado únicamente por `usuarios.supabase_uid`.
- Los hashes bcrypt `$2y$...` de `usuarios.password` son los originales (compatibles con `password_verify()` de PHP). No son contraseñas en texto plano; si se decide autenticar sólo con Supabase Auth, basta con dejar de usar esa columna (no borrar filas).
